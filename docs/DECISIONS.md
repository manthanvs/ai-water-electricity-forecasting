Every non-obvious choice, with reason and alternatives. Newest at the bottom.

## 2026-10-12 - Phase 0

- **Python 3.11.9 installed alongside 3.14.** The machine only had Python 3.14; TensorFlow wheels and the brief both target 3.11. Installed per-user with winget (`Python.Python.3.11`); the project venv `.venv` uses it. Alternative: try TensorFlow on 3.14 - rejected, not the documented environment.
- **LibreOffice installed with winget** (`TheDocumentFoundation.LibreOffice`) at the default path `C:\Program Files\LibreOffice\program\soffice.exe`, which `report/docx_format.py` already finds; no `SOFFICE` variable needed.
- **Repository folder stays `Seminar`** rather than the `water-electricity-forecasting` name suggested in START_HERE.md. Nothing depends on the folder name.
- **Root-level .docx files are git-ignored.** `Seminar Report Format 2526.docx` is byte-identical to `docs/reference/Seminar_Report_Format_2526.docx`; `Seminar_Synopsis_125M1H064_Manthan_Sankpal.docx` has the same text as `docs/reference/Approved_Synopsis_Manthan_Sankpal.docx` (whitespace only); `Seminar_Synopsis_Manthan_Sankpal.docx` is an earlier, longer draft. The canonical copies are in `docs/reference/`. Files left on disk untouched.
- **Model binaries in git.** Git cannot ignore by size, so `models/*.joblib` and `models/*.pkl` (Random Forest / XGBoost dumps, which can exceed 50 MB) are ignored; the small `.keras` files and `model_card.json` are tracked. All models are rebuilt by `python -m wef.cli all`.
- **CLI stage mapping.** Each stage is a module exposing `run(cfg) -> list[Path]` (input files read, checksummed into `results/run_manifest.json`): download -> `wef.data.download`, prepare -> `wef.features.build` (cleaning + features), train -> `wef.models.registry`, evaluate -> `wef.evaluation.backtest`, anomaly -> `wef.anomaly.evaluate`, optimise -> `wef.optimise.pump_schedule`, figures -> `wef.viz.figures`, export-powerbi -> `powerbi.export`. Stages not yet built exit with "not implemented yet (Phase N)". `run_manifest.json` is a JSON list, one record per stage run.
- **`set_seed` seeds TensorFlow only if it is already imported**, so non-deep stages do not pay TensorFlow's import time. `wef.models.dl` must call `set_seed` after `import tensorflow`.
- **requirements.txt pins direct dependencies only**, at the versions that installed here (pandas 3.0.6, TensorFlow 2.21.0, statsmodels 0.15.0, xgboost 3.2.0, ...). A full `pip freeze` would pull Windows-only transitive packages and break the Linux install. Added `pyarrow` (needed for the parquet files of Phase 2). Dropped `pulp`: the pump LP uses `scipy.optimize.linprog`, which the instructions allow, so one fewer dependency.
- **water-benchmark-hub[bwdf] 0.5.2 installs on Windows** (it brings epyt-flow, Hugging Face `datasets` and `wf4bwdf`). Whether its BWDF loader works is checked in Phase 1.
- **Provisional config values** (to be confirmed in the phase that uses them): degree-hour bases 15.5 C heating / 22 C cooling; water validation 10 weeks and test 12 weeks; outlier rule rolling 168 h median with k = 5 MAD; model grids in `config/config.yaml`.

## 2026-10-12 - Phase 1

- **UCI 235 downloaded as the original zip** (`static/public/235/...zip`, 20.6 MB) rather than through `ucimlrepo`, so the raw file can be checksummed and reread offline. `ucimlrepo` stays installed but is unused. Licence CC BY 4.0 (UCI dataset page).
- **UCI clock has no DST.** Every day, including the March and October change days of 2007-2010, has exactly 1440 one-minute rows, so the timestamps are a fixed-offset clock. The source does not document the zone; treated as UTC+1 (CET). Only weather alignment depends on this (at most one hour).
- **BWDF taken from the `wf4bwdf` package** (installed by `water-benchmark-hub[bwdf]`), which bundles `InflowData.xlsx` and `WeatherData.xlsx` - the complete dataset released with Alvisi et al. (2025). Data licence CC BY 4.0 (wf4bwdf README). The files are copied into `data/raw/bwdf/` and checksummed. Real structure: 10 DMAs, hourly, L/s, 2021-01-01 to 2023-03-31 local CET/CEST time (19,679 rows), plus rain, temperature, humidity and wind speed. No separate weather download is needed for water.
- **Primary water series: DMA 3** (residential district in the countryside, population 607, mean 4.3 L/s), chosen by the rule "fewest gaps": 0.53 percent missing, longest gap 31 h. The next best are DMA 2 (3.09 percent) and DMA 5 (3.85 percent). The other nine DMAs are kept for the robustness check.
- **Water holidays: Italy (`holidays` IT).** The wf4bwdf calendar also marks Sundays and 3 November (the city's patron saint) as holidays; that local holiday is noted and will be added as a feature in Phase 3.
- **BattLeDIM: only the files needed were downloaded** (README, configuration, 2018 leak list and leak flows, 2018 SCADA flows and tank level; 13 MB). The 92 MB xlsx files, the 177 MB `L-TOWN_Real.inp`, pressures, AMR demands and all 2019 data were not downloaded; the full Zenodo file list is recorded in the data card. Licence CC BY 4.0 (Zenodo).
- **BattLeDIM leak labels come from `dataset_configuration.yaml`**, which lists every leak with link, start, end, diameter, type and peak time (14 leaks start in 2018; 4 of them never end within 2018-2019). The 2018 fixed-leak report agrees with the end times there.
- **BattLeDIM network inflow = p227 + p235** (the two reservoir inlets). PUMP_1 moves water from tank T1 into area C inside the network, so adding it would double count.
- **Open-Meteo requested in UTC** (`timezone=GMT`, now set in `config.yaml`) instead of Europe/Paris, so daylight saving is resolved once in cleaning and the weather can be shifted to the UCI fixed UTC+1 clock exactly. Period 2006-12-01 to 2010-11-30, no missing values. Licence CC BY 4.0, free for non-commercial use; cite the Open-Meteo Zenodo DOI and ERA5.
- **Dataset citations** added to `report/references.yaml` with `status: seed` (UCI, BWDF paper, BattLeDIM Zenodo record, Open-Meteo, ERA5), with the DOIs read from the source records during download. They are verified in R1.
- **Data cards are generated** by `wef.data.cards` from the raw files on every `download` run, so their numbers cannot drift from the data. `data/cards/` is git-ignored with the rest of `data/`; `docs/DATA.md` carries the same content and is committed.

## 2026-10-12 - Phase 2

- **Time axis rule.** Electricity keeps the meter's fixed clock (no DST, treated as UTC+1); Open-Meteo UTC is shifted by +1 h onto it. Water uses local CET/CEST wall time, because demand follows the wall clock: the repeated autumn hour is averaged (both readings are mean flows over the same wall-clock hour), the absent spring hour becomes a 1-hour gap that the short-gap rule interpolates. Every day therefore has 24 hourly values. Alternative (a UTC index with 23- and 25-hour local days) rejected: it breaks the 24-step D1 target for two days a year for no gain.
- **Minute-to-hour aggregation (electricity).** An hour is the mean of its available minutes when at least 45 of 60 are present; otherwise missing. Hours are labelled by their start (17:00 = 17:00-17:59). Electricity hourly mean kW equals kWh in that hour.
- **Gaps.** Target gaps of up to 3 hours are linearly interpolated (electricity 8 hours, water 77 hours); longer gaps stay missing and are flagged `long_gap` (electricity 7 runs, 428 hours; water DMA 3 1 run, 31 hours). Origins touching them are excluded from training and evaluation in Phase 3. Weather gaps (water humidity, longest 12 h) are interpolated and flagged, since weather is an input, not a reported value.
- **Daily totals need all 24 hours** after short-gap filling; electricity kWh/day = sum of hourly kW; water m3/day = sum of hourly L/s x 3.6. Daily weather: mean, min and max temperature, mean humidity, rain sum.
- **Outliers are flagged, never removed**: rolling centred 168-hour median, flag when |x - median| > 5 x 1.4826 x MAD. Electricity flags 777 hours (household appliance peaks, genuine); water DMA 3 flags 1. The flag is kept as a column for the anomaly chapter and is not used to alter values.
- **Final split dates.** Electricity: train 2007-01-01 to 2009-12-31 (1,089 complete days), validation 2010-01-01 to 2010-06-30 (176), test 2010-07-01 to 2010-11-25 (138). The data ends 2010-11-26 20:00, so 2010-11-25 is the last complete day. Water: train 2021-01-01 to 2022-10-28 (664), validation 2022-10-29 to 2023-01-06 (70 days = 10 weeks), test 2023-01-07 to 2023-03-31 (84 days = 12 weeks). The December 2006 electricity data is used only as lag history for the first training origins.
- **EDA figures use the training period only**, so no test values are inspected before final evaluation. The missing-data map uses all data because it shows availability, not values. Extra EDA figure ids beyond section E: `fig_eda_weekly_heatmap`, `fig_eda_missing`.
- **Slide colours** use a validated colour-blind-safe categorical palette in fixed order (blue, orange, aqua, yellow, magenta, green, violet, red) with neutral text; heatmaps use a single-hue sequential ramp (Blues; Greys in the report). Report PNGs are converted to 8-bit greyscale after saving, so they are greyscale by construction.
- **EDA observations** (for the report): electricity has a morning peak at 07:00 on weekdays and an evening peak around 20:00-21:00, higher and broader at weekends; daily energy falls with temperature (training correlation -0.56, electric heating). Water DMA 3 peaks at 07:00 on weekdays and 09:00 at weekends, with an evening peak around 19:00; daily volume rises steeply above about 20 C (correlation +0.67, summer use).

## 2026-10-12 - Phase 3

- **Origin convention.** Origin = 00:00 of day D; hourly values are hour-beginning, so the newest value known at the origin is D-1 23:00 (and day D-1 for W1). D1 targets the 24 hours of day D; W1 targets days D..D+6. With this convention t-24 h is always known for D1 and d-7 for W1, as the lag rule requires.
- **Feature set.** D1: step, hour/day-of-week/month sine-cosine pairs, weekend, holiday, day before/after holiday; lags t-24, t-48, t-168, t-336; same-hour mean of the last 7 days; mean of day D-1 (an extra rolling statistic computed at the origin); weather at the target hour (temperature, humidity, precipitation) and cooling/heating degree hours. W1: the same calendar without hour; lags d-7, d-14, d-21, d-28; mean of the last 28 days (at least 21 present); target-day weather (mean, max, min temperature, mean humidity, rain) and degree days. Degree bases (15.5 C heating, 22 C cooling) kept from Phase 0 config.
- **Holidays.** `holidays` FR for electricity; IT plus 3 November (patron saint, as in the wf4bwdf calendar) for water. Sundays are covered by the weekend flag.
- **Splits are assigned by origin**, and an origin is kept only if its whole target window lies in the same split (W1 loses the last six origins of each split). Lags may reach back into the previous split; that is information available at forecast time.
- **Gap rule for origins (interpretation of "exclude affected origins").** An origin is excluded from evaluation (`eval_ok = False`) when any of its target values is missing (long gap) or its seasonal-naive input is missing, so every model is scored on the same origins and skill versus naive is always defined. Training rows need a present target. Lag inputs that fall in a long gap stay NaN in the tables; models that cannot take NaN replace them with the training mean of that feature (fit on training data only), and the deep models do the same in scaled space. Reason: excluding every origin whose 14- to 56-day input history touches a gap would remove about 70 percent of the electricity W1 test origins (two gaps in August and September 2010). No target value is ever filled.
- **Evaluable origins** (complete target window and naive input): electricity D1 train 1,082 / val 171 / test 128; electricity W1 1,044 / 144 / 106; water D1 655 / 70 / 84; water W1 638 / 64 / 78.
- **Deep-model tensors** come from the same cleaned series and the same table: a past window (168 h or 56 days) of value plus hour-or-weekday and weekday sine-cosine channels, ending one step before the origin; and a future block with the calendar (and weather) of the target steps. Built in memory by `build.windows`; not saved.
- **Leakage test is a perturbation test.** For a random origin o in train and in test, every target value at or after o is replaced with noise and the tables are rebuilt; all lag and calendar features (and deep-model windows) of rows with origin <= o must be identical. A mutation check (making `lag_24` a 23-hour lag) makes it fail, as it should.

## 2026-10-12 - Phase 4

- **Interface.** `wef.models.registry.Data` holds one resource-horizon table and its cleaned series; every model implements `fit(data, splits)`, `predict(data, origins) -> (n, steps)`, `predict_one(data, origin)`, `save`, `load`, `name`. Predictions for all validation and test origins are written to `results/predictions/<resource>_<horizon>.parquet` (one column per model) and scored by the `evaluate` stage on the shared `eval_ok` origins.
- **Selection and refit.** Every grid candidate is fitted on train only and scored on validation (MAE over all validation `eval_ok` origins). The winner is refitted on train + validation with the same hyper-parameters (XGBoost reuses the number of boosting rounds found by early stopping) and that refit produces the test forecasts. Validation forecasts come from the train-only fit. Full grids with fit times are in `results/tuning.json`.
- **Relative-to-level option.** The water series drops to a new low from November 2022 (validation and test lie in it), and trees cannot extrapolate below the training range: absolute-target XGBoost had validation MAE 48 m3/day for W1 against 9.4 for seasonal naive. Tabular models therefore have a hyper-parameter `relative`: target and lag features divided by the recent level known at the origin (mean of the last 168 h for D1, last 28 days for W1), predictions multiplied back. Chosen on validation: electricity selects absolute for every model, water selects relative for every model. Alternative (always relative) rejected: it costs electricity about 1-4 percent MAE.
- **Ridge** imputes missing lags with the training mean and standardises features (both fitted on training rows); grid alpha x relative. **Random Forest** uses scikit-learn's native missing-value support; grid depth x leaf size x relative, 200 trees. **XGBoost**: subsample 0.8, column sample 0.8, up to 2,000 rounds with early stopping (50) on validation; grid learning rate x depth x relative.
- **SARIMA.** No exogenous inputs (pure SARIMA; weather enters only the learned models). d = 0 and D = 1 are fixed so that AIC is comparable across the grid (p, q) in {(1,0), (1,1), (2,1)} x (P, Q) in {(0,1), (1,1)}; the order with the lowest AIC on the fitting window is chosen and only that one is backtested on validation. Parameters are estimated once (D1: last 8 weeks before the period; W1: all history from the first training day), with at most 50 optimiser iterations. At each origin the state is updated by filtering the history with fixed parameters. Seasonal differencing is done outside the state space (`simple_differencing=True`), about 6 times faster; the full state-space model with the same parameters gives identical forecasts and is used for origins whose previous season contains a gap.
- **Run time.** All Phase 4 models for both resources and horizons train and backtest in about 6.5 minutes (SARIMA electricity D1 alone 5 minutes). Model files are small except the water D1 Random Forest (25 MB), still under the 50 MB limit; `.joblib` files stay git-ignored.
- **Phase 4 gate (validation versus seasonal naive).** All learned models beat seasonal naive on validation for electricity (both horizons) and for water D1, except SARIMA on water D1 (0.241 vs 0.232 L/s). For water W1, SARIMA (23.4 vs 9.4 m3/day) and Ridge (13.3) are worse than seasonal naive on validation; Random Forest (8.8) and XGBoost (8.5) beat it. Reported as is.

## 2026-10-12 - Phase 5

- **Deep-model inputs** (identical for LSTM, GRU, CNN-LSTM): a history window (168 h for D1, 56 days for W1) of the value with hour-or-weekday and weekday sine/cosine channels; and a future block with each target step's calendar, weather and the same lag-rule features the tabular models get (lag 24/48/168/336 h, same-hour 7-day mean, previous-day mean; or lag 7/14/21/28 days and 28-day mean). Two-input network: recurrent encoder (CNN-LSTM: causal Conv1D 32 filters, kernel 3, max-pool 2, then LSTM) joined with the flattened future block, Dense(64, ReLU), Dense(24 or 7) direct multi-output head.
- **Zero-initialised output layer.** First attempt (random init, no per-step lags) gave water W1 validation MAE 28-41 m3/day against 9.4 for seasonal naive: in relative units the target spread is tiny (std 0.05) while a random output layer starts around +-0.5, and with 650 training windows the network could not recover within 60 epochs. With a zero-initialised output layer every network starts at a sensible forecast (training mean, recent level, or seasonal naive) and moves only where validation loss improves.
- **Options chosen on validation**: `relative` (value, lags and target divided by the recent level; as for the tabular models) and `residual` (the head adds a correction to the scaled seasonal-naive forecast), with units in {32, 64}. Layers fixed at 1 so that the grid (8 configurations x 3 architectures x 4 series = 96 fits) trains in about 13 minutes on this CPU. Adam 1e-3, MSE loss, batch 32, at most 60 epochs, early stopping with patience 8 and best weights restored. Batch size reduced from 64 to 32 to give the small water training sets more gradient steps.
- **No refit on train + validation for the deep models**: the early-stopped train-only model produces the test forecasts (refitting would need a fixed epoch count without a stopping signal). This gives the deep models slightly less data than the refitted tabular models; stated in the report.
- **Scaling** fitted on training windows only (future-covariate means and deviations; target mean and deviation for absolute mode); missing inputs inside a window become 0 after scaling. Windows with a missing target are not used for training. Seeds via `set_seed(42)` after importing TensorFlow, with TensorFlow op determinism on.
- **Artefacts**: `models/<resource>_<horizon>_<arch>.keras` (0.2-0.7 MB each) and `models/model_card.json` (architecture, parameters, window, inputs, scaler, epochs run, best epoch, validation loss, training seconds); training curves in `results/training_curves.json` and `fig_training_curves` (viva appendix). Reload reproduces the saved predictions to 1.5e-5.
- **Observation**: the best water W1 deep model stops at epoch 1 (best validation loss at the start), i.e. it stays close to its seasonal-naive starting point; there is too little training data (about 650 weekly windows) for the network to learn a reliable correction. Reported as a limitation.

## 2026-10-12 - Phase 6

- **Selection** over all seven non-naive models by validation MAE: electricity D1 GRU; electricity W1, water D1 and water W1 XGBoost. For electricity W1 and water W1 the selected model is not the best on test (LSTM is); the report says so and the Diebold-Mariano tests show those differences are not significant.
- **Significance**: Diebold-Mariano test on per-origin MAE with the Harvey-Leybourne-Newbold small-sample correction and a two-sided t reference; autocovariance lags h - 1 with h = 1 for D1 (one forecast per day, no overlap) and h = 7 for W1 (overlapping weekly windows). The selected model is compared with the best alternative on test, and additionally with seasonal naive.
- **No-weather ablation** for the best tabular and the best deep model by validation MAE, refitted with the selected hyper-parameters and no weather inputs (columns `<model>_no_weather` in the prediction files; `ablation_no_weather` in metrics.json).
- **Peak MAE is `null` for water** (`n_peak_points` = 0): after the late-2022 drop no test hour or day exceeds the 90th percentile of training demand. Kept as defined in the instructions rather than switching to a test-period threshold. JSON writing now refuses NaN.
- **Robustness check**: XGBoost with the hyper-parameters selected on DMA 3 is trained and tested (D1) on every one of the 10 DMAs with the same splits; results under `water.robustness` in metrics.json.
- **Model comparison figure** shows test MAE divided by seasonal-naive MAE (1 = naive), because kW and L/s cannot share an axis; absolute values are in the report table. **Forecast figures** show the test week (Monday start, 7 evaluable days) whose selected-model MAE is closest to the median weekly MAE - a typical week, not a best case.
- **`results/summary.md` is generated** from metrics.json by `wef.evaluation.backtest.summary`, so it cannot disagree with the numbers.

## 2026-10-12 - Phase 7

- **Water forecaster for anomaly detection.** The anomaly test uses BattLeDIM, a different network from BWDF, so the selected water D1 model type and hyper-parameters (XGBoost, relative-to-level) are retrained on BattLeDIM 2018 network inflow (p227 + p235, hourly) for January-March, without weather or holidays (L-Town is fictional). The same January-March model forecasts both the tuning period (April-June) and the test period (July-December); it is not refitted, as a deployed detector would not be. Leaks are present throughout 2018 (five start in January-March), so the forecaster's "normal" already contains leaks; this is unavoidable with these data and is stated in the report.
- **Splits for detection**: BattLeDIM train 2018-01-01 to 03-31, tuning 04-01 to 06-30 (4 leaks start), test 07-01 to 12-31 (5 leaks start: p654 and p810 incipient, p183, p158, p369 abrupt). Hourly only; the 15-minute series was not used (hourly already resolves the abrupt leaks; YAGNI).
- **Event rules.** Robust z-score on a trailing 168-hour window (strictly earlier hours, median and 1.4826 x MAD); alarm when |z| > k for m consecutive hours, raised at the m-th hour; alarms within 6 hours of the previous event extend it. Isolation Forest (200 trees) on residual, absolute residual, hour, weekday, trailing 24-hour mean and standard deviation, fitted on validation-period features (out-of-sample residuals, the same scheme for both resources); flagged hours become events with a minimum run length. k in {2, 2.5, 3, 3.5, 4, 5}, m in {1, 2, 3, 4, 6}, contamination in {0.005, 0.01, 0.02, 0.05}, minimum run in {1, 2, 3}; chosen by event F1 on validation (ties: fewer false alarms per week).
- **Matching.** Water: an alarm is correct if it falls between a leak's start and min(repair, peak + 7 days) (abrupt leaks peak at their start). Because the 2018 leaks overlap and incipient leaks peak months after they start, these windows cover 72 percent of test hours, so random alarms would already reach precision 0.72. Every score therefore carries `chance_precision`, and water also has a stricter onset score (alarm within 72 hours of the leak start; chance 0.08). Electricity: an alarm is correct if it falls inside the injected anomaly. Recall counts labels that start in the period; delay is first correct alarm minus label start.
- **Electricity INJECTED anomalies.** Injected into copies of the validation period (seed 101) and the test period (seed 202): 6 spikes (x2-4, 1-3 h), 3 level shifts (+30-60 percent, 1-3 days), 2 drifts (linear ramp to +40-60 percent over 3-5 days); non-overlapping, at least 48 h apart, never on long gaps. Labels saved as `data/processed/electricity_val_injected_labels.csv` and `electricity_test_injected_labels.csv` with `label_source = injected`. The selected D1 model (GRU) forecasts the injected series, so injected values also enter its inputs, as they would in operation; for a refitted tabular model the validation residuals would come from a train-only fit.
- **Outputs**: `results/anomaly.json` (per method: parameters, validation and test scores, tuning grid, per-label detections; water onset score; electricity recall by type), `results/anomaly_events.csv` (test-period events for the API, dashboard and Power BI), figures `fig_anomaly_water` (leak starts as dashed lines, since two never end within the period) and `fig_anomaly_electricity` (the test fortnight with the most injected events).

## 2026-10-12 - Phase 8

- **Parameters** in `config/optimisation.yaml`, labelled ILLUSTRATIVE ASSUMPTIONS and sized for DMA 3: tank 150 m3 (min 20 percent, max 95 percent, start and end-of-day floor 50 percent), pump 30 m3/h (about 1.6 times the test-period peak hourly demand), 0.5 kWh/m3. The tariff is a base rate of 1 cost unit per kWh with multipliers off-peak 0.6 (23:00-06:59), peak 1.5 (07:00-10:59 and 18:00-21:59), normal 1.0; no real tariff rate is assumed and savings are reported in percent. Replace with a real schedule (and cite it) if the guide supplies one.
- **LP** with `scipy.optimize.linprog` (HiGHS): hourly pumped volume, tank bounds through cumulative-sum constraints, end level at least the start level. Each test day starts at the same level, so days are independent. A sign error in the end-level constraint (it never bound, and every plan ended at the minimum level) was caught by the perfect-forecast check (it needed corrective pumping) and fixed; `tests/test_lp.py` now checks a toy case with a known optimum and that an exact-demand plan needs no correction.
- **Evaluation against actual demand**: corrective pumping at the hour's tariff when the level would fall below the minimum (within spare pump capacity); overflow above the maximum is spilled and counted; end-of-day shortfall against the start level is topped up in the last hour. Plans from the selected forecast (XGBoost), from the seasonal-naive forecast and from the actual demand (perfect-foresight upper bound). Baselines: demand-following pumping and a level-triggered on/off rule (on below 40 percent, off above 90 percent). The LP was feasible on all 84 test days.
- **Peak alerts.** The rule as specified (forecast daily peak above the 90th percentile of training daily peaks) raises no alert on validation or test: forecasts are smoother than actuals, so their peaks never reach the actual-peak threshold. Reported as is, with a calibrated variant whose alert threshold is the 90th percentile of the model's own validation forecast peaks (chosen on validation). Shiftable energy is measured, not assumed: sub-meters 2 (laundry) and 3 (electric water heater and air conditioner) in peak-tariff hours on alert days, an upper bound since it assumes all of it can move.
- **Example day** for the figure and the API: the test day whose saving against demand-following is closest to the median (`results/pump_schedule_example.csv`).

## 2026-10-13 - Phase 9

- **Shared service layer `wef.service`** (an addition to the layout in CLAUDE.md section 5): the Flask routes are thin wrappers around it and the dashboard calls the same functions directly when the API is unreachable, so the API and the offline fallback cannot diverge. It only reads saved results and models.
- **Endpoints added beyond the specification**, for the dashboard: `GET /api/backtest` (stored rolling-origin forecasts for a date range and models) and `GET /api/optimisation` (optimisation.json). `GET /api/forecast/latest` accepts optional `model` and `origin`.
- **`POST /api/forecast` from arbitrary history.** Requires regular hourly (D1, at least 336 h, ending 23:00) or daily (W1, at least 56 days) non-negative values; the feature builder runs in an `inference` mode that keeps every origin. Weather for the target period comes from the request (`weather`), else from the processed dataset when it covers the dates, else the best no-weather model (from the Phase 6 ablation, by validation MAE) is used and the response says so (`weather_source`). Asking explicitly for a weather model without weather is a 400.
- **Errors** are JSON `{"error": ...}`: 400 for invalid input (unknown resource, horizon or model, malformed history, irregular frequency, too short, negative values, infeasible schedule, unknown override), 404 for unknown routes or missing results, 405 for wrong methods, 500 without a stack trace.
- **Dashboard**: one file, six pages on a sidebar radio (Overview, Forecast, Anomalies, Optimisation, Model comparison, Upload); Plotly charts in the slide palette; a light theme pinned in `.streamlit/config.toml` so the live demo and the report capture look the same on any machine. Every page first calls `/api/health`, so the offline banner appears on every page when the API is down. The response cache is keyed on the API URL. Injected electricity anomalies and illustrative optimisation parameters are labelled on the pages that show them.
- **Tests**: `tests/test_api.py` (every endpoint with valid and invalid input, Flask test client) and `tests/test_dashboard.py` (every page rendered with Streamlit's AppTest, once with no API and once with the API served in a background thread).

## 2026-10-13 - Phase 10

- **Star schema**: five facts (`fact_consumption` hourly actuals; `fact_forecast` every validation and test forecast of every model in long format, with `actual`, `step`, `split`, `eval_ok`; `fact_anomaly` detections and labels with `kind`; `fact_metrics` official scores in long format with `is_selected`; `fact_schedule` per water test day and plan) and three dimensions (`dim_date`, `dim_resource`, `dim_model` with one selected-model flag per task). Every fact carries `date` and `resource`; forecasts and metrics carry `model`. UTF-8 CSV with ISO timestamps (`YYYY-MM-DDTHH:MM:SS`).
